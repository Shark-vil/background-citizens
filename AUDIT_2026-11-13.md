# Background NPCs recent changes audit

What this change does: confirmed damage now drives conflict attribution, witness reactions and arrest escalation. The range also adds lethal weapon learning, stable combat targets, remembered-position pursuit, room sieges and player hostage negotiation.

**Verdict: fix 1–6 first.** There are two action/hook ordering conflicts and four failures to connect new behavior to existing consumers. The implementation cannot be certified free of conflicts or unpredictable decisions.

Русский: [согласованный отчёт](AUDIT_2026-11-13.ru.md).

## Must fix

### 1. [P1] NPC memory refreshes itself while its enemy is hidden

**Locations:** `lua/background_npcs_core/actor/components/sh_enemies.lua:163`, `:173`; `actor/body/sv_npc_body.lua:103`, `:113`, `:120`. Short paths below are relative to `lua/background_npcs_core/`. Integration regression in `69887065`.

**What this is:** `EnemiesRecalculate` should forget an ordinary hidden enemy after 60 seconds. NPCBody also reads the engine's last-seen time.

**Problem:** after checking the timeout, every pass calls `SetEnemy(enemy, remembered_pos)`, including without LOS. NPCBody passes that stale position to `UpdateEnemyMemory`, whose contract updates information as if the enemy had been seen. The following pass treats that write as a fresh sighting.

Trace: sighting at `t=100` → target hides → timeout still permits searching at `101` → writing the old position refreshes engine memory to `101` → the next pass reads `101` → repeat. A model of the documented API contract retains the enemy at `t=180`, with actor observation time `100` and engine time `180`. This was not measured in game; it is an inference from the API contract and code path.

**Fix:** separate observation age from forced engine-memory writes. Do not submit the same stale information every pass. New sightings/reports and body replacement need distinct updates; a write must not count as new visual confirmation.

**If we skip it:** NPCs keep searching without the normal timeout. A nearby hidden enemy can also keep the actor protected from population recycling. NPC and NextBot behavior diverge.

**Regression check:** combine NPCBody with `EnemiesRecalculate`: see a target, lose LOS, update continuously for over 60 seconds. A target without wanted/always-visible must be forgotten; a real new sighting must extend memory. The current pursuit stub's constant `GetEnemyLastTimeSeen() = 0` cannot catch this.

### 2. [P1] Negotiation restores NPC weapons during a siege

**Locations:** `systems/sv_negotiation.lua:26`, `:32`, `:49`; `systems/siege/sv_siege.lua:178`, `:186`. Added in `69887065`.

**What this is:** negotiation and siege both suppress ordinary NPC shooting through `CAP_USE_WEAPONS`.

**Problem:** negotiation saves and removes the enabled bit. The NPC then starts or joins a siege, which saves the already disabled bit. The next negotiation tick excludes siege participants and restores its saved weapon bit during the siege.

Reproduced `negotiation.Tick → Siege.Quiet → negotiation.Tick`: capabilities change `7 → 6 → 0 → 1` using test weapon/door bits `1/2/4`. At the end `actor.siege` is still set while `CAP_USE_WEAPONS` is enabled. This is a single-thread state-restoration conflict, not simultaneous writes from multiple threads. NextBots additionally check `actor.siege`, so this particular failure concerns NPC bodies.

**Fix:** reject `hold_fire` actors in both operator `CanStart` and follower `Join`. Negotiation already excludes active siege actors; these two checks cover the opposite transition without introducing another capability manager.

**If we skip it:** some NPCs can fire during the siege's waiting/movement phases despite the intended ceasefire.

**Regression check:** load both modules together and exercise both transition orders and participant roles. Original capabilities must be restored exactly once when the action ends.

### 3. [P1] Manhack damage attribution depends on EntityTakeDamage hook order

**Locations:** `systems/siege/sv_siege.lua:357`; `actor/events/sv_self_damage.lua:14`; common `ResolveVehicleAttacker` in `api/sv_combat.lua`. Added in `69887065`.

**What this is:** a siege payload stores `bgn_siege_owner`; the separate `BGN_SiegeOwner` handler rewrites its damage attacker to that owner.

**Problem:** damage reactions and attacker rewriting use the same event. File registration order does not establish callback execution order: `hook.Call` iterates with `pairs` and stops at the first non-`nil` result.

Both orders of the actual Lua handlers were reproduced. A police manhack damages a citizen on the owner's team, with team damage disabled:

```text
BGN_SiegeOwner → BGN_ActorTakeDamageEvent
  attacker = officer → shared team → return true → damage blocked

BGN_ActorTakeDamageEvent → BGN_SiegeOwner
  attacker = separate manhack → no shared team → citizen adds manhack as enemy
  attacker then changes to officer → no reaction recalculation → damage allowed
```

**Fix:** resolve the owner synchronously in the common attacker path, before team checks and reactions. Reuse the existing resolver, including an inflictor fallback through that path where needed. Renaming hook IDs or changing include order does not solve this.

**If we skip it:** the same scene can produce different friendly damage and enemy lists. Correct attribution received by later witnesses cannot undo a wrong pre-damage decision.

**Regression check:** permute handlers for friendly/hostile NPCs, players, NextBots and seated actors. Team protection and attribution must agree. This audit reproduced the citizen/manhack counterexample, not that entire permutation matrix.

### 4. [P2] Rebind does not move new position memory and target selection

**Locations:** `api/sh_actors.lua:74`, `:122`; `actor/components/sh_enemies.lua:177`, `:199`. Interaction with new state introduced by `69887065`.

**What this is:** boarding/leaving a car replaces the entity while preserving the Actor and UID. Other actors should remember the same character.

**Problem:** `Rebind` replaces enemy-list entries and `enemy_last_seen` keys, but not `enemy_last_position` keys. After replacing a hidden target, the enemy/time use the new entity while its position remains under the old one. `combat_enemy` and `last_attacker` also keep old body references.

Running the real `Actors.Rebind` in an isolated world gives `HasEnemy(replacement) == true`, a transferred timestamp, no `enemy_last_position[replacement]`, and the old position entry still present. `defense` loses the pursuit destination; stable selection can fall back to another nearest enemy.

**Fix:** transfer `enemy_last_position`, `combat_enemy` and `last_attacker` in the existing Rebind loop. Give the body the transferred position when needed. Move references/values without deep-copying actors. Separately verify intentional siege cancellation when a target boards a vehicle.

**If we skip it:** pursuit stops or changes target after entity replacement; stale position keys remain until actor cleanup.

**Regression check:** use two enemies and replace the hidden selected enemy through boarding/exiting. Preserve its UID, position, knowledge age and recent-attacker priority. Existing conflict rebind tests cover different memory.

### 5. [P2] Weapon choice uses the nearest enemy while combat uses another

**Locations:** `api/sv_combat.lua:128`, `:139`; `actor/components/sh_enemies.lua:177`; `brain/fsm/states/sv_defense.lua:80`. An existing consumer is inconsistent with `69887065` target selection.

**What this is:** `GetEnemy` now preserves a combat target and prioritizes recent attackers/groups. `GetNearEnemy` still means the geometrically nearest enemy.

**Problem:** `defense` and the body use the selected enemy, but `PrepareWeapon → Combat.EquipActor` chooses a metrocop's pistol/stunstick from `GetNearEnemy`. For example, wanted target A remains selected farther away while nearby B has caused little harm. Equipment is chosen for B. The real `EquipActor`, with different stunstick eligibility for A/B, leaves `police_firearm == false` although the selected target requires a firearm.

**Fix:** use `GetEnemy` for this equipment decision, retaining the current arrest-target fallback. Do not replace every `GetNearEnemy` call: fleeing and finding the nearest threat have different meanings.

**If we skip it:** the officer equips a weapon for a different task. Stable target selection does not produce a consistent combat decision.

**Regression check:** two targets with different weapon requirements; vary distance and priority source. Cover NPC/FSM, NextBot/GOAP and arrest with no combat enemy.

### 6. [P2] NextBot unstuck teleports do not use combat-radius protection

**Locations:** `lua/entities/bgn_nextbot.lua:695`, `:720`, `:740`; `api/sv_combat.lua:58`; `docs/systems/brains.md:13`. Incomplete behavior promised by `69887065`.

**What this is:** documentation promises no unstuck teleports while any living known enemy is within 1000 units, inclusive.

**Problem:** `PullOut` and `HandleStuck` only check `actor.siege`. An ordinary `defense` fighter can still reach `SetPos`. The combat-radius predicate is connected to recycling/respawn, but to neither unstuck path.

Executed the actual `HandleStuck` method with an expired stuck timer, a free hidden goal and an actor for which `IsInCombatRadius` returns `true`: `SetPos(goal.pos)` runs without ever asking the predicate. Reading `PullOut` shows the same missing guard for its short teleport.

**Fix:** use existing `Combat.IsInCombatRadius` before both `SetPos` paths, while keeping siege protection. Ordinary movement/jump attempts may remain; the restriction concerns teleportation. Exercise 1000/1000.1 boundaries through the actual consumers.

**If we skip it:** an ordinary stuck fighter teleports within the protected zone. A unit test of the radius predicate passes while the promised scenario remains unimplemented.

## Actual call order

### Loading and updates

```text
autorun/background_npcs.lua
  → SERVER reads loader.txt, sets replicated bgn_loader_active
  → each realm chooses init from its current ConVar value
  → core → config → API → cvars/commands → Actor/components/body/events/update
  → navigation/DV → wanted → arrest → remaining systems, including negotiation/siege
  → FSM states → GOAP → spawner → integrations → UI/debug → postload

BGN_ActorUpdate (shared-budget coroutine; actor list copied)
  → IsAlive → UpdateActor
    → knocked_down: recovery only
    → LOD / pause calculation
    → EnemiesRecalculate (1 s)
    → RecalculationTargets (5 s)
    → rebuild follow path / UpdateMovement when active
    → brain:Update when active (normally 0.2 s near / 1 s far)
```

Order inside `UpdateActor` is fixed. Between actor updates, `budget()` may yield. Negotiation (0.5 s), siege and compliance (0.25 s), hostility and held weapons (1 s) use separate timers. They are not one atomic actor tick. Sorted includes make definitions available; they do not order handlers on one event.

### Damage, witnesses and arrest

```text
EntityTakeDamage
  → independent handlers: victim reaction, arrest protection, LOD/GOAP wakeup,
    lethal metadata, attack time, payload owner rewriting, etc.
    [no guaranteed relative order; see 3]
  → accepted engine damage
  → PostEntityTakeDamage(..., took=true)
    → ConfirmDamage
      → amount/participants/ignore/brawl checks
      → first_attacker:RecordDamage
      → stop further processing for friend-mode pairs involving players
      → player_arrest:RecordDamage for an existing arrest
      → BGN_ConfirmedDamage
        → witnesses / arrest initiation / wanted-time update
        [these callbacks also have no specified relative order]

Seated actor
  → TakeVehicleDamage → BGN_TakeDamageFromNPC → adjusted amount
  → decrement saved.health → BGN_PostVehicleDamage
  → same ConfirmDamage and police harm accounting
  → death: ragdoll / OnNPCKilled / removal
```

Within `ConfirmDamage`, attribution → existing-arrest harm → notification is explicit. This keeps the opening hit that initiates an arrest from being counted as a later violation in that chain. Death has separate events; their full native ordering against post-damage was not measured.

`SetState`: restrictions/`not_stop` → `BGN_PreSetState` → validator → `pre_start` → stop movement/animation → old state's `stop` → assign new state → `start` → `BGN_SetState`. Even `forced` does not bypass all hooks and `pre_start`; it is not unconditional assignment.

## Current behavior tree

This is a composition of FSM, GOAP, events and timers, not a single executable Behavior Tree object. CLIENT displays synchronized states/animations; these decisions belong to SERVER. Shared Actor definitions do not give clients server authority.

```text
Living actor
├─ knocked_down → recovery/free-space check → previous AI
├─ no active threat → FSM: config random / walk / idle / dialogue / scenic, etc.
└─ threat signal
   ├─ direct damage → team protection/hooks → at_damage → enemy
   ├─ confirmed damage to another
   │  └─ witness sees ATTACKER within 2500
   │     ├─ attacker is BGN actor → also front half-space
   │     └─ ResolveEnemy: teams → common enemy → self-defense/initiator
   │        → foreign NPC/player rules → wanted → team enemies → fallback
   ├─ help → teammate within 1000 sees caller → at_protect / AddEnemy
   │  └─ preserve active calling_police
   ├─ enemy sharing → bgn_enemy_share_period (0 disables)
   │  ├─ ordinary teammates see source within 1000
   │  ├─ gangs use visible allies without this branch's radius cap
   │  └─ share last position with its original observation timestamp
   ├─ fear witness → sees scared teammate AND its enemy → at_protect
   ├─ wanted → police receive target; further reaction/arrest rules apply
   ├─ foreign NPC D_HT towards actor → local LOS reaction
   │  └─ hostility to residents/police can cause wanted without a witness
   ├─ lethal weapon [default OFF]
   │  └─ 1 s / ≤800 / LOS + front half-space / learned class → at_damage
   │     └─ this alone invents no damage, initiator or wanted record
   └─ experimental shot sound [separate setting]
      └─ recognized player sound / LOS / ≤2500 → witness reaction

Reaction
├─ ignore / none → caller-specific handling, not one global veto
├─ fear / run_from_danger → flee; ask for help; possible weapon pickup
├─ calling_police
│  ├─ entry: wanted-mode, limit of 2 near a player, PoliceKnows
│  ├─ active call survives LOS loss and subsequent wanted status
│  ├─ selected enemy strictly closer than 300 → fear
│  └─ 7–15 s → report eligible enemies still unknown to police → fear
├─ arrest / arrest_surrender
│  ├─ primary officer handles detention; active protection stops allied fire
│  ├─ subsequent police harm / kill → escalation
│  ├─ >3 distinct innocent BGN victims or victim health <30% → escalation
│  ├─ leave beyond 250 after approach / warning expires → escalation
│  └─ comply → detention countdown → arrest/threat cleanup
└─ defense / retreat → combat FSM; GOAP may plan
   ├─ target: attacker within last 5 s → siege → squad
   │  → saved combat_enemy → nearest living known enemy
   ├─ defense without LOS → remembered position / column; no position → stop
   ├─ LOS → equipment / vehicle pursuit / squad slot / melee / repositioning
   └─ GOAP: highest-priority reachable goal → cheapest FSM action plan
      ├─ police: eliminate; outnumbered: cover → backup → attack
      ├─ gangster: give_up / hide / shelter / survive / eliminate by facts
      ├─ citizen: shelter / hide / fight / flee / report by facts and config
      ├─ held door → breach; desperate non-police → hold_door

         → reserve target/entrance → up to 5 near, others ≥650
         → position within 15 s → wait 12 s
         → door/animation → opening → one manhack/grenade
         → hold 6 s → restore → 60 s shared target cooldown
         → damage/target loss/pocket departure/interruption/50 s → finish

Independent negotiation timer
└─ police / selected player enemy / not siege / nearby frightened non-police
   → hold_fire → offer → warning 5 s before deadline → 20 s limit
   → kill or deadline → failure → block new talks for 120 s
   → no shield for >3 s → end; death/arrest/wanted level down reset block

├─ observe all visible known enemies, not just the nearest
├─ ordinary hidden enemy → 60 s timeout [NPC defect 1]
├─ wanted on initial AddEnemy seeds position without LOS: explicit exception
├─ calm non-fighting NPC feared target → forget after 20 s
├─ body replacement preserves Actor/UID [new memory defect 4]

```

GOAP preserves active calls, sieges, surrender, door actions and knocked-down states against its own replanning. That is not a universal lock against other systems. Picking `GetReactionForProtect` also does not guarantee a transition: state restrictions and hooks can refuse it.

## Checks without an identified defect

- Siege reserves its entry before followers join, without yielding inside that operation. Shared `used` prevents repeat deployment; entity/physics creation failure ends the attempt without repeated release.
- Pocket search is bounded and checks incoming edges, alternative exits, roofs, ladders and floor limits. Incomplete NavMeshes remain a documented limitation, not proof of a physically unique exit.
- New witnesses require attacker visibility. Isolated checks cover arrest boundaries, conflict memory, the 300-unit call boundary, 800-unit weapon boundary and combat-radius predicate.
- Weapon learning stays active with reactions disabled, keeps its cache on script reload, preserves corrupt JSON, excludes specified blast/vehicle kills and retains learned memory on disk-write failure.
- Notice fonts are cached per size per script load. The queue intentionally has no cap. Notification floods and visual screen capacity were not measured; no runtime defect is claimed without a concrete overload case.
- Modern Tools use consistent loader guards; both menus expose lethal reactions; EN/RU keys and 88 new OGG references/headers agree. Audio was not listened to.

## Design questions, separate from confirmed findings

The user confirmed both modes matter. A further question asks whether a hostage must be visible and actually block the firing line, or whether the current distance checks are intended. No reply was available when this report was written.

`Negotiation.Hostage` currently checks neither LOS nor direction/alignment with the firing line. A scared actor beside the player or behind a wall can therefore qualify and stop fire. That is established code behavior; calling it a design bug without the user's answer would be premature.

Documentation also says both that doors must be fully open before deployment and that release begins while a leaf is moving. Code permits opening doors and checks clearance. The siege description still promises muted voices although current code speaks siege lines. Align the EN/RU wording after confirming intended behavior; do not change gameplay merely to match contradictory prose.

## API research sources and reproducibility

The installed `garrysmod/lua/includes/modules/hook.lua` was read directly: it uses `pairs` and exits on non-`nil`. That is primary evidence for the installed Lua implementation.

Targeted queries: `hook.Add`, `GM:PostEntityTakeDamage`, `GM:OnNPCKilled`, `NPC:UpdateEnemyMemory`, `NPC:GetEnemyLastTimeSeen`. Primary public sources, read 2026-11-13:

- [Official hook.lua implementation](https://github.com/Facepunch/garrysmod/blob/master/garrysmod/lua/includes/modules/hook.lua): unordered iteration and early exit.
- [hook.Add](https://wiki.facepunch.com/gmod/hook.Add): callback short-circuit contract.
- [PostEntityTakeDamage](https://wiki.facepunch.com/gmod/GM:PostEntityTakeDamage): `wasDamageTaken` semantics; also documents an attacker position/angle issue during this event. This is an additional limit on post-damage visual checks, not a new defect measured here.
- [OnNPCKilled](https://wiki.facepunch.com/gmod/GM:OnNPCKilled): death parameters; it does not establish the complete ordering of native events.
- [UpdateEnemyMemory](https://wiki.facepunch.com/gmod/NPC:UpdateEnemyMemory) and [GetEnemyLastTimeSeen](https://wiki.facepunch.com/gmod/NPC:GetEnemyLastTimeSeen): basis of item 1's model. A live scene on this engine build was not checked.

Used Ponytail/Ponytail Review and targeted API research under Universal Modder game-research-websearch. Archives, tool downloads, screenshots and community contact were unnecessary. This local report is sufficient; no external field note was published.

**Fix order:** 1–3 address incorrect memory and processing/restoration conflicts; 4–6 finish connecting new logic to its consumers. No new architecture, dependency or wholesale AI rewrite is needed.

**Not checked:** native gameplay and the integrations listed above. **Risk:** until fixed, equivalent scenes can yield different damage protection and shooting suppression; this audit is not release approval.
